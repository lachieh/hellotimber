## Grounding and decision

`PlanCaptureSet` currently owns import declarations (`scripts/capture-set.ts`),
discovered once through `capture-sets/index.ts`. `import-captures.ts` resolves REF
sources into LCD/tick/sound fixtures and per-plan indexes. It is not transactional:
a late import failure may leave earlier files written. Extraction reads only
committed goldens. `extract-resources.ts` currently imports two text-run tables,
one override table and three widget tables directly. `harvestGlyphs` is pure;
widget extraction first derives timelines from asserted tree goldens, then applies
explicit probe timelines. Sprite matching and timeline deduplication choose the
first matching entry. Declaration order therefore affects generated bytes.

The acceptance harness already reports pending fixtures as todos and fails an
asserted fixture without a scenario. The guard also rejects scenarios for pending
or foreign fixtures. Resource use grants no behavioral coverage exemption.
`regenerate` is a Vite+ task in `packages/nokia-os/vite.config.ts`, not a package
script. Tests and regeneration must never read REF.

Two complete alternatives were compared:

- **A: extend `PlanCaptureSet.resources`.** One existing index export registers
  imports and extraction evidence. A shared import-safe discovery function validates
  plan identity; extraction reads resource declarations without invoking capture
  callbacks. Plan-owned resource modules hold substantial data. The cost is loading
  import configuration modules during extraction; these modules already have no
  top-level REF IO. This keeps a new plan's single registration authoritative.
- **B: separate `PlanResourceSet` registry.** Resource modules have a second barrel,
  with the same declaration vocabulary and validation. It isolates extraction from
  capture configuration, but creates two plan lists and requires consistency checks
  when a new file is omitted from either barrel. No current consumer needs this
  separate lifecycle.

Select **A**. Both support pending resource evidence and deterministic extraction;
A needs fewer coordination points and is safer when the next editor changes only
one plan. Do not retain the old tables as another input path. Preserve font names
and metrics as shared vocabulary. Make widget groups/kinds declarative strings,
with one owner per timeline-kind mapping, so later plans can add resource evidence
without extending shared enums/tables.

Design exploration and independent judgment use GPT-6.1 Sol only. Task IDs:
`node:delegated-task:command%3Amcp%3Ab118cc8b-b4ad-47bc-8cf8-9721d9aa98d8%3Adelegate-task%3Ap29-retry-design-1`
and
`node:delegated-task:command%3Amcp%3Ab118cc8b-b4ad-47bc-8cf8-9721d9aa98d8%3Adelegate-task%3Ap29-retry-judge-2`.
The exploration and independent judge both favored A. The judge required import-safe
discovery, complete migration, explicit batch order, extensible kind mappings, global
validation before writes and unchanged status rules; all are included below. B was
rejected for its second registry and partial-edit coordination cost. No cross-provider
review was used because the user requires GPT-6.1 Sol for all delegated work.

## Consumer contract

`PlanCaptureSet.resources?: ResourceDeclarations` contains:

- `textRuns`: golden id → image name → `TextRun[]`. A glyph sample is a
  single-character run, with a `GlyphOverride` when its cell advance/bearing cannot
  be measured from that specimen. No second glyph-sample interpretation path.
- `glyphOverrides`: existing `GlyphOverride[]`; one writer for each semantic key
  `(kind,font,char)` or `(touch,font,pair)`.
- `spriteBatches`: `{ order, entries: SpriteCrop[] }[]`.
- `timelineBatches`: `{ order, entries: ProbeTimeline[] }[]`. Each probe targets
  exactly one `node` or `name`, with golden, kind and optional `fromFrame`.
- `timelineGroups`: kind → ordered sprite-group names. Group names are reusable;
  one plan owns each kind mapping. Empty groups remain valid for cursor prompts.

Batch order is required serialization/matching order, not optional priority.
Existing contiguous blocks retain positions 10,20,30 (sprites) and 10,20,30,40
(probes); new plans use a distinct integer such as 180 or 200, with increasing
positions if they need multiple blocks. Duplicate positions in the same category
fail. Entry order within a batch is preserved. There is no central sprite-ID list.

A new plan adds its owned modules plus its one export in `capture-sets/index.ts`:

```ts
// scripts/capture-sets/20-calculator.ts
import type { PlanCaptureSet } from "../capture-set.ts";
import { calculatorResources } from "../resource-inputs/20-calculator.ts";
export const calculator: PlanCaptureSet = {
  plan: "20",
  lcd: calculatorCaptureSet,
  resources: calculatorResources,
};
```

The capture callback above is the plan's real importer, not a stub to add here.
Plan 20's `/` run/resolution and named rate notes live in its resource module;
existing note sprites are reused. Plan 18 registers glyph-manifest transcriptions,
header/mode/counter crops and message-note probes in the same shape. Plan 18c
registers chat/content text, pictures as widget sprite crops and named notes;
content reconstruction outside this vocabulary remains its own task.

For example a plan-owned input can use committed evidence immediately:

```ts
const resources: ResourceDeclarations = {
  textRuns: {
    "glyphs/small-001": { specimen: [{ font: "small", text: "/", top: 16 }] },
  },
  glyphOverrides: [{ kind: "advance", font: "small", char: "/", advance: 5 }],
  spriteBatches: [
    {
      order: 180,
      entries: [
        {
          id: "message/envelope",
          group: "message",
          golden: "sms/notice",
          image: "notice",
          x0: 1,
          x1: 9,
          y0: 0,
          y1: 5,
        },
      ],
    },
  ],
  timelineGroups: { "message-note": ["message"] },
  timelineBatches: [
    { order: 180, entries: [{ golden: "sms/saved", kind: "note", name: "message-saved" }] },
  ],
};
```

Coordinates/advance in this illustrative shape must come from that consumer's
verified captures; they are not firmware facts authorized by plan 29.

## Ownership and invariants

The capture index owns fixture identity/status. Resource declarations own evidence
interpretation, which may reference another plan's fixture. The extractor owns
loading, harvesting, cropping, matching and timeline derivation. Firmware only
reads generated resources. Register generated tree runs through plan 14 without
hand-editing them. Import-safe discovery never runs `lcd`/`ticks`/`sounds`.

Reject duplicate plans, semantic text runs (golden/image/font/band), overrides,
sprite IDs, batch positions, kind mappings and explicit timeline targets, including
identical duplicates. Diagnostics identify both plan owners. Different bands in
one image may be combined (existing profile-box supplements). Validate indexed
LCD identity, image presence, font bands and crop rectangles before extraction;
missing files, ink-free crops and malformed timelines fail rather than disappear.
Reject an unknown probe kind or a kind's missing sprite group. Explicit probes may
replace an automatic tree-node timeline, as existing progress probes do; two
explicit writers may never replace each other.

A missing barrel export fails a file-to-registration test. Tests also prohibit
extractor/test consumers from bypassing the registry through direct imports of
resource-input modules. All declarations migrate; no fallback or optional legacy
branch remains. Extraction computes all resources before its existing write loop.
A write-time IO failure remains recoverable by rerunning deterministic generation.

Pending workflow: import new LCD, glyph and picture fixtures as `pending:18`,
`pending:20` or `pending:18c`; consume them for resource extraction and keep an
acceptance file with only genuinely asserted scenarios. Add verified behavior
and its driver before promoting each fixture through the importer. Existing
fixtures stay in their original owner's index and acceptance file. Never use
`knownGaps` to conceal absent scenarios, add scenario shims, or exempt resource
stills from asserted coverage. Pending suffixes use the existing plan-number grammar.
